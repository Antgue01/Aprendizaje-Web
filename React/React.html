React

React crea Single Page Applications (SPA). Un único `index.html` se carga y su contenido se actualiza dinámicamente en el navegador. Visualmente parece que navegas, pero lógicamente, todo ocurre en la misma página, sin recargas completas.

El principio de diseño ideal en React es que cada elemento o sección de la página sea un componente distinto, fomentando la modularidad y reutilización, por lo que el archivo index.html de una aplicación React contiene un único <div> con un id="root" (o similar), donde todo el contenido de la aplicación se inyecta y gestiona mediante JavaScript.

Enrutamiento

Para enrutar, es decir, asignar las URL a páginas de nuestra web de forma que cuando se escriba una URL nuestra, React tiene que saber cómo reconfigurar el DOM (o la View en native). Para ello usamos el módulo react-router-dom, que se descarga de yarn con el comando:

yarn add react-router-dom
¡Copiado!

Después, usamos el import correspondiente:

import { BrowserRouter as Router, Routes, Route, Link } from 'react-router-dom';
¡Copiado!

El componente Router se encarga de gestionar las rutas de nuestra aplicación, y además es donde se construye el nav que sobrevivirá entre páginas. Debe envolver toda la aplicación para que el enrutamiento funcione correctamente.

Si tiene componentes padre, estos también sobreviven entre páginas.

Dentro de Router, ponemos tanto los componentes visuales que formen nuestro nav (que en cada apartado del nav deben incluir el componente <Link to = { "ruta"} /> ) como el componente <Routes>, dentro del cual irán cada una de las rutas de la aplicación.

Para ello utilizamos el componente <Route path = { "ruta"} element = { <Componente />} /> , donde path es la URL y element es el componente que se muestra al acceder a esa URL (generalmente una página).

<Router> {/*Construcción visual del nav con <Link> */} <nav className='main__nav'> <ul> <li> <Link to={"/"}> <i className='bi bi-house-door'> </i> </Link> </li> <li> <Link to={"/rotating"}>Botón Rotativo</Link> </li> </ul> </nav> {/*Rutas lógicas*/} <Routes> <Route path="/" element={<App />} /> <Route path="/rotating" element={<RotatingButtonPage />} /> </Routes> </Router>
¡Copiado!

Podemos poner variables en las rutas, para ello utilizamos el símbolo : en la definición de la ruta, y en el componente al que redirigimos lo declaramos como prop y usamos el hook useParams.

<Route path="/pagina/:nombre" element={<MiPagina />} />
¡Copiado!

Luego, en el componente <MiPagina/> :

import { useParams } from 'react-router-dom'; export default function MiPagina() { const { nombre } = useParams(); // Hacemos lo que sea con el parámetro }
¡Copiado!

Así, al acceder a la URL /pagina/Pepe, recibiremos Pepe en el prop.

JSX

Es una sintaxis desarrollada para React que permite usar los componentes como etiquetas HTML. JSX se transpila (compilar de un lenguaje a otro) a JavaScript puro antes de ejecutarse en el navegador.

Esto hace que sea muy flexible, ya que podemos usar JSX dentro de bucles, con condicionales, variables,etc.

Para insertar variables y expresiones en JSX, usamos { }. Por ejemplo:

const image = <img src = {myImg.uri} alt = {myImg.alt}/>
¡Copiado!

Para definir componentes, se puede hacer principalmente de dos formas, a través de una función normal o a través de una función flecha.

function Hola() { return <h1> Hello World </h1>; }
¡Copiado!
const Hola = () => { return ( <h1> Hello World </h1> ); }

Los componentes pueden recibir argumentos en la función que los define para mostrar contenido personalizado o hacer lógica, son los llamados Props y, como dijimos antes, se insertarían con { } en el componente.

Para Pasar los props al componente, se hace como si fuera un atributo de la etiqueta HTML. Después, en el componente, se definen como un objeto deserializado.Por ejemplo:

En la App

<Hola name={"Adri"} age={23} />
¡Copiado!

En el componente

const Hola = (props) => { const { name, age } = props; return (<h1 className="title">Hey wassup, {name} are u {age} years old?</h1>); }
¡Copiado!

Pasar componentes como props

Esto es relevante sobre todo en Typescript. En React hay dos tipos para los componentes: ComponentType<Props> (la plantilla genérica <Props> es opcional) por una parte y ReactNode por otra.

Un componente es una función que recibe un objeto del tipo de la plantilla (Props ), por lo que podemos pasarle props desde fuera sin re-renders innecesarios.

Al invocarlo, se hace simplemente pasando la función.

Por otra parte, un nodo es una etiqueta JSX o TSX, por lo que los props que le pasemos serán fijos.

Al invocarlo, se hace entre {}.

Types.ts

// Archivo Types.ts (o bien sin los exports antes de implementar tu componente) import { ComponentType, ReactNode } from 'react' export type CustomCompNode = { //Esto es un nodo, un tsx. node: ReactNode; } export type CustomComp = { // Esto es un componente con dos props: un string y un número. // SIEMPRE VAN A SER ESOS DOS PROPS //Las variables de tipo componente tienen que empezar POR MAYÚSCULA Comp: ComponentType<{ text: string, number: number }>; // Esto son los props que le pasamos al componente props: { texto: string, numero: number } } //Si declaramos con plantilla que extienda otro tipo, //cada vez que lo invoquemos // PODEMOS HACER POLIMORFISMO DE COMPONENTES //En este caso, cuando definamos el componente, //en la signatura tenemos que añadir <T extends OtroTipo export interface BaseComp { baseText: string, baseNumb: number, } export interface DynamicComponent<T extends BaseComp> { Comp: ComponentType<T>, props: T } //Estas dos interfaces ya incluyen lo de BaseComp export interface CustomComp1 extends BaseComp { extendedAttr1: string } export interface CustomComp2 extends BaseComp { extendedAttr2: number }
¡Copiado!

Hooks

Los Hooks son funciones que permiten a los componentes de React acceder a funcionalidades del ciclo de vida y del estado sin necesidad de crear una clase.

import { useState, useEffect } from 'react';
¡Copiado!

use State

useState permite añadir un estado local a un componente funcional.

Primero, tenemos que importarlo de react, y luego llamamos a la función useState(valor inicial), que devuelve un array con el estado y la función que hay que llamar para cambiarlo. Nosotros entonces lo declaramos en un array deserializado y ya podemos usarlo:

import { useState } from'react'; //Declaramos el estado const [state, setState] = useState(0); //Cambiamos el estado setState(1); // ... return <h1>{state}</h1>;
¡Copiado!

Si para cambiar el estado USAMOS el valor actual (por ejemplo, un contador, que usa el valor actual y le suma 1), en lugar de llamar a la función con la expresión que actualiza el valor directamente, le debemos pasar una función flecha cuyo argumento es el valor actual. Así:

setState(prev => prev + 1 );
¡Copiado!

Esto evita bugs , sobre todo si cambiamos el valor varias veces en poco tiempo.

useEffect

El useEffect se usa para responder a cambios en el estado o props. Recibe una función y un array de dependencias.

La idea es que la función que pasamos se ejecute cada vez que alguna de las dependencias cambie, y si le pasamos una lista vacía, se ejecutará una sola vez, al montar el componente.

Si en el efecto creamos algo externo a React, como un intervalo, un listener o una conexión a una API externa, debemos limpiarlo al desmontar el componente, devolviendo una función de limpieza dentro del efecto. Por ejemplo, hacemos clear del intervalo o quitamos el listener.

De hecho, si no estamos en modo build, React ejecutará dos veces el efecto al montar el componente, y si ocurre algún error, significa que no hemos limpiado del todo el efecto, ya que debe soportar que el componente se monte, se desmonte y se vuelva a montar.

¡Importante!

Si leemos o usamos el valor de un estado en el useEffect, NO podemos cambiar su valor, ya que si lo hacemos entraremos en un bucle infinito.

useRef

Como tras cada re-renderizado se pierden los valores de las variables, se utiliza este hook para crear variables que sobrevivan a estos re-renderizados.

Tiene un atributo current, que es donde guardamos y usamos la referencia que queremos mantener.

useContext

Si necesitamos pasar el mismo prop a muchos hijos(con el mismo o distinto valor), crearemos un contexto, que es como un objeto al que pueden preguntar los hijos y busca hacia arriba hasta llegar al primer padre que lo tiene .

Para ello, creamos un archivo loqueseaContext.js en el que creamos el contexto:

¡Copiado!

En el padre al que queremos preguntar envolvemos los hijos en nuestro contexto:

//Padre.tsx import { ThemeProvider } from './ThemeProvider.tsx'; export default function Padre({ level, children } ) { return ( //cosas del componente que renderizar //... <ThemeProvider value={level}> {children} </ThemeProvider> ); }
¡Copiado!

En el hijo usamos el hook que exportamos:

//Hijo.tsx import { useTheme } from './ThemeContext.tsx'; export default function Hijo() { const { theme, changeThemeFunc } = useTheme(); //usamos theme o la función changeThemeFunc }

useMemo

Cachea el resultado de una función para que no se vuelva a ejecutar en cada renderizado, lo que mejora el rendimiento. Pensado para funciones que tardan en ejecutarse.

La primera vez que se renderiza el componente, se ejecuta la función y se guarda el resultado.

En renderizados posteriores, si las dependencias no han cambiado, se devuelve el resultado guardado.

En cuanto cambia una dependencia, se vuelve a ejecutar la función y se actualiza el valor.

La sintaxis es la siguiente:

useMemo(fn, dependencies);
¡Copiado!

useCallback es el equivalente para funciones en lugar de resultados de funciones.

La regla para usarlos es:

Si DENTRO de la función de un componente DECLARAMOS algo Y LO PASAMOS COMO PROP a un hijo, o bien HACEMOS UNA FUNCIÓN MUY COSTOSA DENTRO de la función del componente, USAMOS estos hooks.

ReactNative

La principal diferencia es que tiene componentes nativos que se importan desde react-native. A los componentes se les da estilo a partir del prop style, que recibe un objeto con las propiedades de estilo, como si fuera CSS, pero en camelCase.

Lo ideal es crear este objeto con Stylesheet.create(). Aquí en lugar de selectores, creamos un objeto en el que cada propiedad tiene como clave la clase y como valor el objeto de estilo.

Además, no hay Grid, solo hay Flex.

Para renderizar listas, se utiliza el componente FlatList en lugar de hacer arrays. (Este componente ya tiene scoll, no usar una ScrollView con él).map(). Otra opción es SectionList si queremos agrupar los elementos en secciones.

Estos componentes reciben un prop data con el array de datos (objetos) a renderizar y un prop renderItem que recibe una función que devuelve el componente (obviamente, debe recibir los props necesarios) a renderizar por cada elemento del array. Además, podemos usar el prop keyExtractor para especificar una clave única para cada elemento.

Permiten callbacks como onEndReached para detectar cuando se llega al final de la lista y cargar más datos, o onRefresh para refrescar la lista.

const DATA = [ { id: 0, nombre: 'First Item', {/*lo que sea*/} }, {/*...*/} {/*Este es el render Item*/} const Item = ({nombre}) => ( <View style={styles.item}> <Text style={styles.title}>{nombre}</Text> </View> ); {/*En el componente:*/} <FlatList data={DATA} {/*Este es el componente generado al declarar const Item*/} renderItem={({item}) => <Item nombre={item.title} />} keyExtractor={item => item.id}/>
¡Copiado!

Si queremos scroll en una lista, debemos envolverla en un componente ScrollView y usar la propiedad contentContainerStyle para dar estilo a la parte de dentro.

Además, a este scroll podemos envolverlo con un KeyboardAvoidingView para evitar que el teclado cubra los campos de entrada. Le pondríamos el prop behavior en padding y un keyboardVerticalOffset para ajustar la posición.

C++ y JNI

JNI (Java Native Interface) es la interfaz que permite comunicar código Java/Kotlin con código nativo escrito en C/C++.

El flujo de ejecucion sigue la estructura: Java → JNI → C++. El código C++ se compila dentro de una biblioteca nativa (.so en Android) ejecutada directamente por el proceso de la aplicación.

JNI — Apuntes básicos

Método native en Java

Para declarar en Java un método cuya implementación estará escrita en C/C++, se utiliza la palabra clave native.

public native void printHello();
¡Copiado!

La palabra clave native indica que el método está declarado en la capa de Java, pero su lógica real reside en la capa nativa. Una vez declarado, se invoca como cualquier otro método de Java.

Cargar la biblioteca nativa: Antes de utilizar las funciones nativas, Java debe cargar la biblioteca desde un bloque estático utilizando System.loadLibrary:

static { System.loadLibrary("musicar_android"); }
¡Copiado!

Si CMake genera el archivo libmusicar_android.so, se omite tanto el prefijo lib como la extensión .so.

Implementación y Convención de Nombres

JNI localiza automáticamente la función C++ mediante una convención de nombres estricta estructurada como Java_paquete_Clase_metodo.

Por ejemplo, para el paquete com.musicar, la clase MusicarMediaLibraryService y el método printHello, la firma nativa en C++ debe ser Java_com_musicar_MusicarMediaLibraryService_printHello. Los puntos del paquete se reemplazan por guiones bajos (_).

Para evitar el name mangling (sobrecarga de funciones) de C++ y garantizar que JNI encuentre el símbolo exacto, la función debe declararse con enlace C usando extern "C":

extern "C" { JNIEXPORT void JNICALL Java_com_musicar_MusicarMediaLibraryService_printHello(JNIEnv* env, jobject thiz) { // Implementación nativa } }
¡Copiado!

Análisis de la firma de compilación JNI:

  • JNIEXPORT: Macro que marca la función para ser exportada y visible públicamente desde la biblioteca compartida.
  • JNICALL: Macro que define la convención de llamada de la plataforma destino.
  • JNIEnv*: Puntero a la estructura de la interfaz JNI. Proporciona las funciones necesarias para interactuar con la JVM (crear objetos, llamar métodos de Java, manipular arrays y cadenas, etc.).
  • jobject / jclass: Si el método de Java es de instancia, recibe un jobject que representa a esa instancia. Si el método es static, recibe un jclass representando la clase.

Mapeo de Tipos JNI

JNI define tipos primitivos específicos para realizar la correspondencia entre los tipos de Java y C++:

  • int → jint
  • long → jlong
  • boolean → jboolean
  • float → jfloat
  • double → jdouble
  • String → jstring
  • Object → jobject
  • Class → jclass

Logging nativo en Android: Para escribir en Logcat desde C++ se utiliza la cabecera nativa de Android <android/log.h> e invocamos a la función __android_log_print() de la biblioteca liblog (debe estar enlazada dentro del CMakeLists.txt):

#include <android/log.h> __android_log_print(ANDROID_LOG_INFO, "MusicarNative", "Mensaje desde C++: %d", 42);
¡Copiado!

Arquitectura de Separación (Adapter Pattern)

Estructuramos el código dividiendo la responsabilidad en dos capas:

1. C++ Puro: Lógica del dominio/reproductor independiente que no incluye cabeceras de Android ni JNI.
2. Adaptador JNI: Capa puente que entiende JNI, traduce los datos provenientes de Java/Kotlin e invoca las funciones del C++ puro.

En Android Studio: File → New → New Module y seleccionamos una biblioteca nativa/Android.

Le damos un nombre, por ejemplo musicarNative, y dejamos C++ Standard en Toolchain Default.

Android Studio crea la carpeta del módulo, su build.gradle.kts, el CMakeLists.txt y la estructura de código nativo. El módulo queda registrado en settings.gradle.

Comprueba que el módulo aparece incluido con su nombre exacto, por ejemplo include(":musicarNative").

¿Por qué? settings.gradle es donde Gradle conoce qué módulos forman parte del proyecto; el nombre debe coincidir con el que después usaremos como dependencia.

musicarNative/build.gradle.kts

El módulo utiliza el plugin com.android.library porque no genera un APK propio: genera una biblioteca que puede consumir app.

En android { ... } se configura externalNativeBuild para que este módulo use su propio CMakeLists.txt y la versión de CMake que tengamos instalada.

También se configura aquí la versión de Android mínima y el NDK que utilizará el módulo.

¿Por qué? Así musicarNative tiene su propio build nativo y no toca el CMake que utiliza el módulo app para React Native.

app/build.gradle

En las dependencias de app se añade una dependencia de proyecto apuntando al módulo local, por ejemplo implementation project(":musicarNative").

¿Por qué? Esto le dice a Gradle que la aplicación utiliza esa biblioteca, por lo que al construir app también construirá musicarNative y empaquetará su biblioteca nativa.

No se utiliza una cadena como com.example.musicarnative: esa notación es para dependencias externas publicadas, no para módulos del propio proyecto.

CMakeLists.txt

CMakeLists.txt describe a CMake qué construir; CMake después utiliza el compilador y el toolchain configurados para realizar la compilación.

cmake_minimum_required(...): indica la versión mínima de CMake que acepta el proyecto.

project(...): da nombre al proyecto de CMake.

add_library(...): crea una biblioteca e indica qué archivos fuente la forman. STATIC genera una biblioteca estática y SHARED una biblioteca compartida (.so en Android).

El primer argumento de add_library es el nombre del target/librería que estamos creando. Si generamos, por ejemplo, una biblioteca llamada musicar_android, en Android el archivo resultante será libmusicar_android.so y, al cargarla desde Java, se utiliza ese mismo nombre sin el prefijo lib ni la extensión .so.

find_library(...): busca una biblioteca que proporciona el sistema/NDK, como log.

target_link_libraries(...): indica contra qué bibliotecas debe enlazarse un target para resolver sus dependencias.

El CMake del módulo no debe incluir ReactNative-application.cmake ni trabajar con appmodules: nuestra biblioteca es independiente de React Native.

CMake: targets, STATIC y SHARED

Un target es algo que CMake sabe construir, como una biblioteca o un ejecutable. Con add_library creamos un target que representa una biblioteca y le damos un nombre.

STATIC crea una biblioteca estática: sirve para agrupar código que después se enlazará dentro de otro target. SHARED crea una biblioteca compartida: queda como un archivo independiente que puede cargarse en tiempo de ejecución.

Por eso, una forma sencilla de entender STATIC en nuestro proyecto es como un grupo reutilizable de código común. No es obligatorio usarlo: también podemos crear directamente una SHARED con todos los .cpp del core y el adaptador de una plataforma, pero ESTARÍAMOS EJECUTANDO EL MISMO ENLACE SOBRE LOS MISMOS ARCHIVOS, RALENTIZANDO EL BUILD.

# Versión mínima de CMake que acepta este proyecto. cmake_minimum_required(VERSION 3.22.1) # Nombre del proyecto de CMake. project(MusicarNative) # Target que agrupa el código común. # Aquí podríamos tener A.cpp, B.cpp, Player.cpp, Queue.cpp, etc. # STATIC no es un "objeto": es una biblioteca estática que después puede enlazarse # dentro de uno o varios outputs. add_library( musicar_core STATIC core/A.cpp core/B.cpp core/Player.cpp ) # Target final para Android. # SHARED produce la .so que Android puede cargar en runtime. (o la .dll para windows, .so para linux, etc) # El adaptador es solo la parte que conoce JNI/Android. add_library( musicar_android SHARED adapters/android/AndroidAdapter.cpp ) # Busca una biblioteca que Android ya proporciona. # Primer argumento: variable que elegimos nosotros para guardar el resultado. # Segundo argumento: nombre con el que CMake busca la biblioteca. # "log" corresponde a la biblioteca liblog de Android. find_library( ANDROID_LOG_LIB log ) # El target Android usa el código común y la biblioteca de logging. target_link_libraries( musicar_android musicar_core ${ANDROID_LOG_LIB} )
¡Copiado!

Varios .cpp dentro del mismo target

Si el core tiene A.h + A.cpp y B.h + B.cpp, no se crea un target por cada clase. Los dos .cpp pertenecen al mismo target.

Si A utiliza B, A.cpp incluye B.h. CMake solo necesita que A.cpp y B.cpp estén incluidos en musicar_core; las relaciones entre las clases las resuelve C++.

Para añadir más clases al core, simplemente se añaden sus .cpp al mismo add_library(musicar_core ...).

STATIC no es obligatorio

También podríamos crear directamente una biblioteca SHARED para Android incluyendo el core y el adaptador en el mismo target.

Y al hacer Windows podríamos crear otra SHARED reutilizando los mismos archivos del core y cambiando solo el adaptador:

musicar_android → A.cpp + B.cpp + Player.cpp + AndroidAdapter.cpp

musicar_windows → A.cpp + B.cpp + Player.cpp + WindowsAdapter.cpp

La ventaja de un target STATIC separado es simplemente tener el código común agrupado en un target reutilizable; no es necesario para reutilizar esos archivos.

¿De dónde salen los nombres de find_library?

El primer nombre, por ejemplo ANDROID_LOG_LIB, lo eliges tú: es la variable donde CMake guardará la biblioteca encontrada.

El segundo nombre, log en este caso, es el nombre que CMake tiene que buscar entre las bibliotecas disponibles para esa plataforma. Para saberlo hay que consultar cómo se llama la biblioteca que proporciona la plataforma.

En Android buscamos log porque la plataforma proporciona liblog, que contiene __android_log_print.

Turbo Modules

Es la forma de comunicar JS con la parte nativa de la plataforma.

Necesitamos 3 archivos: la especificación, la Implementación y el paquete.

La especificación es un archivo Typescript cuyo nombre de archivo DEBE empezar por Native. En ella exportamos una interfaz que debemos llamar Spec que extienda de TurboModule con todos los tipos y funciones del módulo. Además, haremos un export por defecto con el nombre del módulo.

export interface Spec extends TurboModule { // En este caso exportamos un método; loadLists(path: string): Promise<PlayList[]>; } // El nombre DEBE empezar por Native; export default TurboModuleRegistry.getEnforcing<Spec>("Nombre del módulo");
¡Copiado!

Después, copiaremos esto en el package.json. El name es el nombre que le daremos al conjunto de módulos y el javaPackageName el nombre que le daremos al paquete de java que va a crear.

"codegenConfig": { "name": "Nombre del conjunto de módulos", "type": "modules", "jsSrcsDir": "specs", "android": { "javaPackageName": "com.nombreParaPaquete" } },
¡Copiado!

Además, ejecutaremos el siguiente comando para generar las especificaciones en código nativo (aunque realmente se ejecuta también al hacer la build):

cd android gradlew generateCodegenArtifactsFromSchema
¡Copiado!

En Java y Objective C, implementaremos para Android e iOS respectivamente la especificación. Para ello, crearemos una clase que extienda de la clase generada, que tendrá el nombre que le dimos en el string de Typescript + Spec.

Además, React genera las clases WritableMap y WritableArray , con métodos push y pull para cada tipo de dato básico. Además, exporta un tipo Promise para los métodos asíncronos que exportemos, al que llamaremos a los métodos resolve() y reject() a los que les pasaremos lo que queramos devolver.

Hay que tener mucho cuidado porque al estar en dos lenguajes distintos, si no ponemos los datos adecuados en el WritableArray (o map), ningún compilador nos avisará, pero dará excepción.

Finalmente, crearemos la clase del paquete, que la llamaremos igual que el string que definimos como nombre + Package y haremos que extienda de BaseReactPackage.

Tanto en React como en React native, se usa una combinación de las librerías i18n y react-native-localize.

Lo primero que hay que hacer es instalarlas:

Opcionalmente, para evitar almacenar las traducciones localmente (en móvil lo ideal es ALMACENARLAS), instalamos esta otra librería:

yarn add i18next-http-backend

Después, en la raíz del proyecto configuramos i18n en un archivo i18n.ts:

import i18n from 'i18next'; import { initReactI18next } from 'react-i18next'; import * as RNLocalize from 'react-native-localize'; // imports de los archivos de traducción import enCommon from './locales/en/common.json' import esCommon from './locales/es/common.json' // 1) Recursos agrupados por idioma y namespace. Aquí tenemos los archivos almacenados const resources = { en: { common: enCommon, }, es: { common: esCommon, }, }; // 2) Detector sencillo que usa la configuración del sistema const detectDeviceLanguage = () => { const locales = RNLocalize.getLocales(); if (locales && locales.length > 0) { // languageCode devuelve 'en', 'es', 'fr', ... return locales[0].languageCode; } return 'es'; }; i18n .use(initReactI18next) .init({ resources, lng: detectDeviceLanguage(), // idioma del sistema fallbackLng: 'es', // idioma si no hay traducción ns: ['common'], // namespaces, es decir, traducciones separadas por módulos //para no tener un solo archivo gigante defaultNS: 'common', interpolation: { escapeValue: false, // no escapar, React se encarga format: (value, format, lng) => { if (format === 'uppercase') return String(value).toUpperCase(); if (format === 'lowercase') return String(value).toLowerCase(); if (format === 'number') return new Intl.NumberFormat(lng).format(value); if (format === 'datetime') return new Date(value).toLocaleString(lng); return value; }, }, react: { useSuspense: false, // en RN conviene false para evitar Suspense issues }, }); export default i18n;

¡Copiado!

Además, podemos usar funciones para crear loops, secuencias o retrasos con withRepeat(), withSequence() y withDelay()

Ahora bien, necesitamos crear un objeto de estilo que soporte sharedValues. Para ello, usamos la función useAnimatedStyle(función factoría). La función factoría simplemente debe devolver un objeto de estilo. Por ejemplo:

const scaleDown = useAnimatedStyle(() => ({ transform: [{ scaleY: scaleShared.value }], opacity: opacityShared.value }));
¡Copiado!

Este objeto de estilo se pasa a un componente de Reanimated. Por ejemplo, <Animated.View/>. Reanimated tiene versiones para la mayoría de componentes nativos para aceptar animaciones.

De todas formas, si tenemos componentes de librerías o complejos, podemos convertirlos para que sus props acepten sharedValues. Para ello, pasamos el componente por la función createAnimatedComponent(comp), que recibe un componente y te devuelve su versión convertida. CONVIENE MEMOIZARLO para poner la animación correcta de nuevo.

A estos componentes les podemos animar los props con la función useAnimatedProps(factoría).

const AnimatedCircle = Animated.createAnimatedComponent(Circle); export default function App() { const r = useSharedValue<number>(20); const handlePress = () => { r.value += 10; }; const animatedProps = useAnimatedProps(() => ({ r: withTiming(r.value), })); return ( <View style={styles.container}> <Svg style={styles.svg}> <AnimatedCircle cx="50%" cy="50%" fill="#b58df1" animatedProps={animatedProps} /> </Svg> <Button onPress={handlePress} title="Click me" /> </View> ); }
¡Copiado!

También podemos gestionar gestos como Pinch mediante eventos, y podemos usar la función withDecay() para controlar la inercia del gesto (por ejemplo que el usuario haga swipe más rápido o más lento).

SQL

La idea que sostiene todo lo demás: en SQL no buscas datos, describes una tabla nueva a partir de tablas existentes. Entrada tabla(s), salida tabla. Y como la salida es una tabla, puede ser la entrada de otra cosa. Todo lo demás son formas distintas de fabricar esa tabla.

Un detalle que aclara mucho: la tabla resultante es conceptualmente un conjunto sin orden. SQL no garantiza en qué orden salen las filas a menos que lo pidas explícitamente.

Cómo pensar una consulta

Una sentencia tiene siempre las mismas cláusulas y se escriben en un orden fijo, que no es el orden en el que se evalúan:

SELECT -- qué columnas quiero en el resultado FROM -- de qué tabla salen las filas JOIN -- con qué otra tabla las combino, y por qué columna (ON) WHERE -- qué filas descarto GROUP BY -- cómo las agrupo (sólo si agregas) HAVING -- qué grupos descarto (sólo si agrupas) ORDER BY -- en qué orden las entrego LIMIT -- cuántas
¡Copiado!

El orden lógico de evaluación es otro: primero FROM / JOIN, luego WHERE, GROUP BY, SELECT, ORDER BY y por último LIMIT. Esto explica cosas que si no parecen caprichos: un alias que inventas en el SELECT no lo puedes usar en el WHERE (el WHERE ya pasó), pero sí en el ORDER BY, que viene después. Cuando algo no compile, mira dónde estás en esta escalera.

Es una tubería, y por cada tramo pasa un conjunto de filas. Cada cláusula recibe el conjunto que le dejó la anterior y entrega otro:

FROM recibe nada devuelve filas de una tabla JOIN recibe filas devuelve filas MÁS ANCHAS (añade columnas) WHERE recibe filas devuelve MENOS filas (nunca cambia columnas) GROUP BY recibe filas devuelve una fila por grupo SELECT recibe filas devuelve filas con OTRA FORMA ORDER BY recibe filas devuelve las mismas, secuenciadas LIMIT recibe filas devuelve menos filas
¡Copiado!

Lo importante de ahí: hasta el SELECT, todas las columnas de todas las tablas implicadas siguen disponibles. Por eso el WHERE puede filtrar por una columna que luego no aparece en el resultado. El SELECT es el recorte final, no la selección de con qué trabajas. De ahí sale el error mental más común: creer que el SELECT es lo primero que ocurre porque es lo primero que se escribe. Es casi lo último.

El método, en seis pasos:

1. Di en castellano qué es una fila del resultado. Literalmente termina la frase «quiero una fila por cada ______». Es la decisión más importante y todo lo demás se deriva de ella; a eso se le llama el grano de la consulta. Si no puedes terminar la frase con un sustantivo único y claro, la consulta todavía no está pensada y ninguna sintaxis te va a salvar.

2. ¿De qué tabla sale una fila de ésas? Esa es tu tabla del FROM. Cuando el grano es una relación (un hijo dentro de un padre, una compra de un cliente), la tabla de partida suele ser la tabla de la relación, no la de las entidades. Es un reflejo que cuesta adquirir: la tendencia natural es empezar por la entidad «importante», y casi siempre es la elección equivocada.

3. ¿Qué datos necesito que no estén en esa tabla? Cada respuesta es un JOIN. Y para cada uno, pregúntate por qué columna se corresponden las filas: ésa es la condición del ON. Si no sabes contestar eso, no sabes cómo se relacionan las tablas y tienes que mirar el esquema antes de seguir.

4. ¿Qué filas sobran? Eso es el WHERE. Aquí van las condiciones de negocio, y los valores concretos van como parámetros, no escritos en el texto.

5. ¿Qué columnas quiero, y con qué nombre? Eso es el SELECT. Aquí añades columnas calculadas o constantes si las necesitas, siempre con AS si las vas a leer desde código.

6. ¿En qué orden? El ORDER BY, con las claves en cascada.

JOIN

Existe porque el modelo relacional reparte la información. Una entidad vive en su tabla, y una relación de muchos-a-muchos vive en una tabla propia que sólo guarda pares de ids (más lo que sea propio de la relación, no de ninguno de los dos extremos). Para reconstruir la vista completa hay que volver a juntar.

El mecanismo conceptual es producto cartesiano más filtro: combina cada fila de la izquierda con cada fila de la derecha, y quédate con las parejas que cumplen una condición. Esa condición es el ON. JOIN pega a lo ancho: añade columnas a la fila.

X Y X JOIN Y ON X.k = Y.k k a k b k a k b 1 p 1 z --> 1 p 1 z 2 q 3 w (2 y 3 no casan: se caen)
¡Copiado!

El motor no lo hace así de verdad (usa los índices), pero pensar así te dice qué esperar. En particular: si te olvidas el ON, te llevas el producto cartesiano entero, N×M filas. No es un error de sintaxis: es una consulta válida que devuelve una barbaridad.

Variantes que importan:

INNER JOIN (el JOIN a secas): sólo las parejas que casan. Lo que no casa desaparece de los dos lados.

LEFT JOIN: todas las filas de la izquierda pase lo que pase; si no encuentran pareja, las columnas de la derecha salen a NULL. Es lo que usas cuando «puede no haber».

Y una distinción que confunde a todo el mundo: ON no es WHERE. El ON dice cómo se emparejan las filas; el WHERE descarta filas del resultado. En un INNER JOIN da igual dónde pongas la condición. En un LEFT JOIN no: una condición en el ON afecta a si hay pareja (y si no la hay, la fila izquierda sobrevive con nulos), mientras que la misma condición en el WHERE elimina esas filas y convierte tu LEFT JOIN en un INNER JOIN sin que te enteres.

Dos detalles de sintaxis que necesitas: los alias de tabla (dar un nombre corto a una tabla en el FROM/JOIN) son obligatorios cuando la misma tabla aparece dos veces en la consulta, porque si no, no hay forma de decir a cuál de las dos te refieres. Y cuando dos tablas tienen una columna con el mismo nombre, hay que cualificarla con la tabla o su alias, o el motor se queja de ambigüedad.

UNION

Si JOIN añade columnas a una fila, UNION añade filas a la tabla. Son perpendiculares: UNION pega a lo alto.

A B A UNION ALL B k v k v k v 1 p 7 z --> 1 p 2 q 2 q 7 z
¡Copiado!

Como el resultado tiene que seguir siendo una tabla (y una tabla tiene forma fija), ambos lados deben aportar el mismo número de columnas, en el mismo orden y con tipos compatibles. Ojo: SQL no empareja por nombre, empareja por posición. Los nombres de columna del resultado los pone la primera mitad; los de la segunda se ignoran.

UNION es el operador de teoría de conjuntos: elimina duplicados. Para saber qué está duplicado tiene que comparar todo con todo, y en la práctica eso significa ordenar internamente: cuesta. UNION ALL es concatenación pura: no mira nada, no ordena nada, no descarta nada. Salvo que de verdad quieras deduplicar, UNION ALL es lo correcto, y no sólo por rendimiento: UNION puede comerse filas legítimamente repetidas.

Cuando juntas dos consultas que no traen exactamente lo mismo, el truco es que el SELECT es una proyección, no una lista de columnas. Lo que pones ahí no tiene por qué venir de ninguna tabla: puede ser una constante (un número, un texto, un NULL), un cálculo, una condición (que produce 1 o 0), una expresión condicional CASE WHEN ... THEN ... ELSE ... END (el if de SQL), o COALESCE(a, b, c), que devuelve el primer argumento no nulo.

Ese es el mecanismo que te deja fabricar columnas que no existen: una constante distinta en cada mitad de un UNION te da una columna que distingue de dónde vino cada fila, y un NULL literal te rellena un hueco donde el otro lado sí tiene dato.

ORDER BY y NULL

No forma parte de fabricar la tabla: se aplica al entregarla. Por eso va al final del todo, y por eso sobre un UNION se escribe una sola vez y ordena el conjunto ya combinado, no cada mitad por su lado.

Varias claves = orden lexicográfico sobre tuplas. Como ordenar palabras: compara la primera letra; sólo si son iguales mira la segunda. ORDER BY k1, k2, k3 compara por k1; si empatan, por k2; si vuelven a empatar, por k3. ASC / DESC se aplican a cada clave por separado.

Cada clave se evalúa fila a fila, y puede ser cualquier expresión. Esto es lo que hace que un orden así sea siempre transitivo: cada fila produce su tupla mirándose sólo a sí misma, sin saber contra quién va a competir. No hay forma de que la regla cambie según el par.

Y ahí está el error a evitar cuando ordenas en código en vez de en SQL: si escribes un comparador que decide qué regla usar según con quién compara (por ejemplo «si uno de los dos no tiene orden, comparo por nombre»), la relación deja de ser transitiva. Se puede construir A < B < C < A. En JavaScript eso te da un orden raro y ya; en C++ es comportamiento indefinido: std::sort asume la transitividad para saber cuándo parar y puede leer fuera del rango. La STL lo llama strict weak ordering, y la parte que suele pillar desprevenido no es la transitividad de < sino la de la equivalencia: si a y b son «iguales» para el comparador, y b y c también, tiene que serlo a y c. Regla práctica: haz que cada elemento produzca su tupla de claves y compara tuplas.

NULL no es un valor, es «desconocido», y SQL usa lógica de tres valores. NULL = NULL no da verdadero: da desconocido. Por eso x = NULL nunca casa con nada y existe un operador aparte, IS NULL.

Pero ORDER BY tiene que colocar esas filas en algún sitio: no puede decir «no sé». Así que se define arbitrariamente que todos los nulos van juntos a un extremo. SQLite los pone primero en ascendente. Si quieres lo contrario se pide explícitamente con NULLS LAST sobre esa clave. La alternativa portable, útil en motores que no la tengan: ordenar primero por la expresión columna IS NULL, que vale 0 o 1, y sólo después por la columna; el bloque de los 0 (no nulos) va delante del de los 1.

Importante: si no dices dónde van los nulos, el motor decide por ti y no avisa. No hay error ni aviso: el silencio es una decisión tomada por SQLite.

Parámetros

Un literal escrito dentro del SQL forma parte del texto de la consulta. Un parámetro es un hueco que se rellena después, ya compilada. Existen por dos razones: el texto nunca se mezcla con los datos (un valor con una comilla dentro no puede alterar la estructura de la consulta, que es lo que evita la inyección SQL), y la forma y los datos quedan separados, así que la consulta se compila una vez y se puede reejecutar con otros valores.

Tres formas de escribirlos en SQLite:

? -- posicional anónimo: CADA ? ES UN PARÁMETRO DISTINTO, numerado por orden de aparición ?1 -- posicional explícito: ?1 repetido en varios sitios es EL MISMO parámetro, se enlaza una vez :nombre -- con nombre: igual que el anterior pero legible
¡Copiado!

Esto muerde con UNION: si el mismo id aparece en el WHERE de las dos mitades y usas ? sin numerar, son dos parámetros y hay que enlazar los dos. El que se quede sin enlazar vale NULL, y como columna = NULL nunca es cierto, esa mitad no devolverá jamás una fila y no habrá ningún error que te lo diga.

Desde C++ el ciclo es prepare → bind → step en bucle mientras devuelva SQLITE_ROW → column_* para sacar cada campo → finalize. Dos trampas clásicas: los índices de bind empiezan en 1, los de column empiezan en 0, y sqlite3_column_int es de 32 bits (existe sqlite3_column_int64 para lo que no quepa; un valor grande se trunca en silencio). El finalize conviene ponerlo en un guard RAII y no repetido en cada return: si una excepción se cuela entre el prepare y el finalize, el statement se queda sin liberar.

prepare compila el texto SQL a bytecode de la máquina virtual de SQLite; ese objeto compilado es el sqlite3_stmt. Puedes ejecutarlo, hacerle reset, cambiarle los parámetros y volver a ejecutarlo sin recompilar. Guardarlo en un miembro en vez de compilar y destruir en cada llamada es lo que se llama «cachear el statement», y no tiene nada que ver con cachear datos. Cuidado si el código es recursivo: reutilizar el mismo statement mientras un nivel de arriba lo está recorriendo lo rompe.

Formarla ejecutándola

Nunca escribas la consulta entera y la ejecutes al final. Escribes un trozo, lo ejecutas, miras el resultado, añades el siguiente. Con LIMIT puesto mientras exploras, para no llenar la pantalla.

La secuencia es la del método: primero sólo FROM con todas las columnas, para ver qué pinta tiene la tabla de verdad. Luego añades un JOIN y cuentas las filas: si tenías 7 y ahora tienes 7, bien; si tienes 21, ese JOIN multiplicó y hay que entender por qué antes de seguir. Luego el WHERE. Y sólo cuando el conjunto de filas es el correcto te pones a recortar columnas en el SELECT y a ordenar.

Contar filas después de cada JOIN es el hábito que ahorra la mayoría de los ratos perdidos.

Un fichero SQLite es un fichero suelto que cualquier herramienta puede abrir; no hace falta la app para nada. En el PC: DB Browser for SQLite (GUI, tiene una pestaña «Execute SQL» donde escribes y ves la tabla debajo) o sqlite3.exe, la consola oficial. Depurar SQL desde el código es horrible: escríbela fuera y pégala cuando funcione.

Y para el desarrollo, mejor una BD de prueba fabricada a mano que los datos reales. No es comodidad: con datos reales no sabes qué tendría que salir, así que mires lo que mires no sabrás si está bien. Con tres listas anidadas y cinco canciones repartidas por ti, sí. ¡Copiado!

Cierra la app del todo antes de copiar (al cerrar limpiamente el WAL se integra), o cópiate los tres ficheros.

Diagnóstico

Casi todo lo que sale mal es uno de estos tres síntomas:

Salen más filas de las que esperabas. Un JOIN está multiplicando. O la condición del ON no es suficientemente específica, o la relación no es la que creías (crees que es uno-a-uno y es uno-a-muchos). Comprueba el grano.

Salen menos filas, o faltan las «vacías». Un INNER JOIN se está comiendo las filas sin pareja. O quieres un LEFT JOIN, o hay una condición sobre la tabla de la derecha metida en el WHERE que anula el LEFT JOIN.

Salen columnas a NULL que no esperabas. O el dato es nulo de verdad en la BD, o vienen de un LEFT JOIN que no encontró pareja. Distinguir cuál de las dos cosas es te dice si el problema está en los datos o en la consulta.

Y el que no es de SQL pero cuesta lo mismo: una consulta correcta que devuelve cero filas porque un parámetro se quedó sin enlazar. No hay error. Si una mitad de un UNION nunca aparece, mira los bind antes que el SQL.
